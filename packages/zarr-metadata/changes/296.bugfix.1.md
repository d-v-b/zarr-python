Fixed two gaps introduced while scoping entity shapes by extension point.

**Entity rules at `data_type` and `chunk_key_encoding` never ran.** Shape
validators were registered for four extension points but dispatchers for
only two, so `entity_rule` accepted a registration at the other two and
the rule then silently never fired — the exact silent-pass failure the
registry exists to prevent. All four points now dispatch, and
`test_registry.py` asserts that every shape-modelled field has a
dispatcher so the gap cannot reopen. The `struct` data type gains the
first rules this unblocks: field names must be non-empty and unique
within a struct, both promised by `StructField`'s docstring and neither
expressible in a TypedDict.

**Object-form entity metadata was rejected.** `{"name": "uint8"}` and
`{"name": "string"}` were invalid while the bare names were valid. The
spec makes `{"name": ...}` the base form and the bare string the optional
short-hand when no configuration is required, and `zarr_metadata.model`
already accepted both — so `model` and `rules` disagreed about the same
document. Both spellings are accepted again; a configuration member on an
entity that takes no configuration is still an `unknown_key`.

Nested `data_type` positions — `cast_value`'s target type and a struct
field's type — are now judged by the same shapes a top-level `data_type`
gets, recursively. Previously a bare `"numpy.datetime64"` was invalid at
the top level (its configuration is required) and silently fine inside a
struct field.
